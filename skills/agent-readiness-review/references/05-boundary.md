# 边界：与 skill-reviewer 类竞品的分工（防误读）

> 本技能最大的生存风险是**被误用成"又一个 skill 质量审查"**——字节官方 Skill Reviewer 等 10+ 竞品已在该红海。本文件是评审时的边界裁判。

## 评审对象对照表

| 问题 | skill-reviewer 类（竞品） | **本技能** |
|------|--------------------------|-----------|
| 这个 Skill 写得好不好？ | ✅ 它们的活 | ❌ 不答 |
| description/触发词质量？ | ✅ | ❌ |
| 渐进披露结构？ | ✅ | ❌ |
| 知识增量、反模式示例？ | ✅ | ❌ |
| **上线会不会出事？** | ❌ 不答 | ✅ 我们的活 |
| 上下文会不会烂？ | ❌ | ✅ |
| 权限/注入/资金风险？ | 部分（危险模式扫描） | ✅（Harness 级强制点） |
| 中断后能不能续？ | ❌ | ✅ |
| 成本可控吗？ | ❌ | ✅ |

## 快速判定口诀

评审请求进来时，先问自己：**用户想知道的是"写得好不好"还是"敢不敢上生产"？**
- 前者 → 建议改用 skill-reviewer 类技能（本技能不适用的场景要写进报告）；
- 后者 → 用本技能，且**报告中不要出现"description 写得不够好"这类文案建议**（越界即稀释差异化）。

## 与运行时评测平台的分工

Langfuse / Braintrust / DeepEval / Promptfoo 等：**动态评测**——接入代码、跑 trace、测真实表现（延迟/成功率）。
本技能：**静态就绪度评审**——读方案/目录，零接入，测"工程纪律是否就位"。

两者互补关系：本技能评审通过（S/A 级）→ 值得接入评测平台做动态验证；动态评测发现的问题 → 回流本技能复评（如 R3 错误路径用例）。

## 与 skill-dev-kit 的联动

`skill-dev-kit`（技能固化与发布工具包）管"**造 + 发布检查**"（16 项清单、双平台发布）。
本技能管"**上生产前门禁**"。
建议闭环：dev-kit 发布完成 → 自动触发本技能评审 → 报告归档进 dev-kit 的复盘体系。

## 一句话差异化（对外）
