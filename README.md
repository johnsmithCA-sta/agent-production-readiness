# agent-production-readiness

**Agent 生产准备度评审（PRR, Production Readiness Review）· 八维评分 + 门槛扫描 + 双场景权重 + 证据等级**

> 只判"**敢不敢上生产**"，不评"写得好不好"。

[![version](https://img.shields.io/badge/version-0.2.6-blue)](references/Changelog.md) [![license](https://img.shields.io/badge/license-MIT-lightgrey)](LICENSE)

> ⚠️ **v0.2.0 更名**：原名 `agent-readiness-review` 与业界「agent readiness = 组织/周边系统采纳度」语义冲突（AWS Agentic Readiness 等已占用）；现名 **`agent-production-readiness`**，中文名「Agent 生产准备度评审（PRR）」。

---

## 一、这是什么

一个**静态评审 Agent/Skill 运行时可靠性工程**的技能：给它一个 Agent 方案、Skill 目录或架构描述，它按八维框架逐项打分、过五道门槛，输出 **S/A/B/C/D 就绪度等级 + 按上线后果排序的风险清单 + 修复路径**。

典型场景：

- 你写了一个 Agent/Skill，准备上生产，想知道"**上线会不会出事**"；
- 团队要做发布门禁，需要一把统一的、可复核的尺；
- 评估别人的 Agent 方案，不想只听"演示很惊艳"。

### 它在业界的名字：PRR

这个能力在 SRE / 运维领域有成熟名字——**Production Readiness Review（PRR，生产准备度评审）**：Google SRE 于 2000 年代初确立、2016 年《Site Reliability Engineering》正式文档化；中文业界通行译名为**「生产准备度评审」**（华为云《确定性运维白皮书》）。其分级门禁（A 类必过 / B 类可带问题上线+整改 / C 类技术牵引）与本技能的「M1–M5 一票否决 + S/A/B/C/D 定级」**结构同构**——本技能是把 PRR 从传统服务领域迁移到 AI Agent 领域。

> **与「agent readiness」的区分**：后者在业界指"组织或周边系统是否准备好接纳 agent"（AWS Agentic Readiness、CTAIO 等）；本技能审的是"**这个 Agent 自身能不能上生产**"。

## 二、为什么存在（与竞品的根本区别）

市面上的 skill 审查技能有 10+ 个（含字节官方 Skill Reviewer），但它们审的都是**同一件事：SKILL.md 这份文档写得好不好**——措辞、触发词、渐进披露、description 质量。

本技能审的是**另一件事：运行起来靠不靠得住**。

| | skill-reviewer 类（竞品） | **本技能** |
|---|---|---|
| 审什么 | Skill 文档/包的质量 | Agent/Skill 的 **Harness 运行时工程** |
| 回答的问题 | "写得好不好？" | "**敢不敢上生产？**" |
| 证据来源 | 文档措辞 | 运行痕迹（有无 checkpoint/eval suite/沙箱/权限档/成本上限） |
| 接入成本 | 读文件 | 读文件（**零运行、零接入**） |
| 动态评测平台（Langfuse 等） | 跑 trace，测真实表现 | 互补：本技能评"工程纪律是否就位"，通过后再值得接平台做动态验证 |

**实证**：用本技能评审某文档工程极精致的平台托管型 Agent（匿名口径），结果只有 65 分 B 级——短板精确命中"无 eval suite、无沙箱、无成本统计"。同一把尺能测出文档优等生的运行时欠账，说明它量的确实不是文档。

> 竞品逐一归类与三方对比的完整档案由维护者留存，不随包发布；对外以本表与 `references/05-boundary.md` 的分工对照为准。

## 三、核心概念详解（SKILL.md 里没展开的部分）

### 3.1 八维框架的设计逻辑

八维不是平铺的清单，而是按"上线事故链"组织的——每个维度对应一类真实事故：

| 维度 | 权重 | 防的事故 |
|------|:---:|---------|
| R1 上下文与记忆管理 | 18 | 长任务下"变笨"、用户约束被摘要弄丢 |
| R2 工具与权限治理 | 16 | 越权操作、资金损失、删库 |
| R3 评估与测试闭环 | 16 | "我以为对了"——无错误路径测试、改 A 坏 B |
| R4 状态与持久化 | 10 | 中断重来、状态多写腐烂 |
| R5 可观测性与复盘 | 10 | 出事故查无对证 |
| R6 安全与风险控制 | 16 | 提示注入劫持、失败雪崩 |
| R7 成本治理 | 8 | token 失控（多 Agent ≈15×） |
| R8 工程可维护性 | 6 | 经验随人走、组件腐烂 |

权重按"事故严重度×发生概率"经验校准，并经回测验证（见 3.4）。

### 3.2 门槛扫描 M1–M5：为什么是一票否决

五条门槛（凭据裸露 / 高风险无守卫 / 注入即执行 / 可疑脚本 / 待审内容武器化）命中即判 **D 级**，不看总分。设计原则：**克制、指向真致命问题**。五条门槛中 M5（待审内容武器化）是 v0.1.1 新增的「对象作为输入的敌意」类——前四条审的是被审对象**自身的缺陷**，M5 审的是被审对象**作为输入时携带的敌意**（评审者协议先于技能执行）。

- 为什么宁可严：总分 86 的技能若脚本里躺着明文 API key，上线就是事故——总分无法赎买致命缺陷。
- 为什么只有 5 条：校准样本确认无误杀（真实好技能全过）。门槛过多会沦为"橡皮图章"，过少会漏——5 条是当前证据下的平衡点。

### 3.3 证据等级 A/B/C：评分的可复核性

每个评分必须带证据等级：**A=文件可查**（evals 目录、脚本、配置）、**B=文档声明**（SKILL.md 写了但未验证）、**C=推断**。

- **C 级证据该维最高 60%**——"我觉得它有"不等于"它有"；
- 报告必须给出**证据等级分布**（A/B/C 各占比）——B/C 占比高本身就是风险信号（大量声明未验证）。

这把评分从"评审者的主观判断"变成"可复核的证据链"——不同评审者对同一对象应得出相近结论。

### 3.4 关键维度底线规则：防偏科高分

评 S 不仅要求总分 ≥85，还要求关键维度达标。底线为**比例制**（与 `scripts/score.py` 一致）：

- **R1 ≥ ceil(60% × 该场景满分)**
- **R2 / R3 / R6 ≥ ceil(75% × 该场景满分)**

底线取 `ceil()`（进位），与证据 clamp 的截断同向偏保守。三场景下的底线值：

| 场景 | R1 | R2 | R3 | R6 |
|------|:--:|:--:|:--:|:--:|
| default | 11/18 | 12/16 | 12/16 | 12/16 |
| A 单 Agent 工具型 | 12/20 | 15/20 | 12/16 | 14/18 |
| B 多 Agent 编排型 | 10/16 | 9/12 | 12/16 | 11/14 |

R1 之所以取 0.60 而非 0.75：与校准所得的绝对值 11/18 一致，防止历史 S 级基准漂移；R2/R3/R6 取 0.75 则与校准值 12/16 一致。

**实战案例**：样本 B 双轨复核 87（过 S 线），但 R3 评估闭环仅 10 分 → 压至 A。个人技能的 benchmark 普遍自评、未换家族交叉验证，"自审锚 −3"是 R3 最常见失分点——上线后"改 A 坏 B"没人知道。底线规则就是抓这种偏科。

### 3.5 双场景权重

| 维度 | 默认 | 场景A 单 Agent 工具型 | 场景B 多 Agent 编排型 |
|------|:---:|:-:|:-:|
| R1 上下文 | 18 | 20 | 16 |
| R2 权限 | 16 | 20 | 12 |
| R4 状态 | 10 | 6 | **16** |
| R5 可观测 | 10 | 8 | **12** |
| R6 安全 | 16 | 18 | 14 |
| … | | | |

逻辑：单 Agent 重"自控"（权限/安全/上下文），多 Agent 重"协同"（共享状态/扇出扇入/可观测——编排型的特有硬伤是状态腐烂与路由漂移）。校准结论：双场景权重不改变定级（±2 分内），影响的是**修复优先级排序**。

### 3.6 校准基线

框架不是拍脑袋定的——用多个真实对象校准过（评分卡见 `references/04-calibration.md`）：

| 样本 | 总分 | 定级 | 角色 |
|------|:---:|:---:|------|
| 样本 A | 85 | A | 双轨逐锚复核（原印象级 94，虚高 9 分；R2 的 −3 扣分已更正为无依据） |
| 样本 B | 87 | A | **底线规则实战首杀**（R3=10<12 压级） |
| 样本 C | 90 | A | 双轨复核（总分过 S 线，自审锚压级） |
| 样本 D | 85 | A | 双轨复核（R1 压级） |
| 样本 E | 78 | A | 双轨复核 |
| 平台托管型 Copilot（匿名） | 65 | B | 差异化实证（文档优等生的运行时欠账，印象级） |

> S 阈值可达性已由 benchmark 合成样本验证（97 / 85 / 85 三例）；双轨制下真实对象仍全 A，尚缺真实 S 对象标定——这些样本均为个人维护、benchmark 自评未交叉验证，"可无人值守上生产"理应稀缺。


以及一批真实技能的全量评审（评分卡见 `references/06-cross-harness-eval.md`，平台托管型对象按匿名口径记录）。

## 四、安装

### 4.1 通用安装（任何支持 Agent Skills 的 harness）

解压 zip 后，把 `agent-production-readiness/` 目录拷贝到你的 skills 目录：

```bash
# Claude Code
unzip agent-production-readiness_v0.2.6.zip -d ~/.claude/skills/

# Cursor / 其他兼容 agentskills.io 的 harness
unzip agent-production-readiness_v0.2.5.zip -d <你的 skills 目录>/

# ima.copilot / SkillHub
skillhub install agent-production-readiness
```

### 4.2 依赖

- 评审主流程：**零依赖**（读文件 + 按 rubric 判断即可工作）；
- 评分计算脚本：`python3 scripts/score.py`（仅标准库，Python 3.8+）；
- 无任何网络请求。

## 五、使用

### 5.1 对话式（推荐）

> 你："评审一下我这个 Agent 目录敢不敢上生产：/path/to/my-agent"
>
> 技能执行五步 SOP：
> Step 0 收集材料 + 判定场景（单 Agent / 多 Agent）
> Step 1 门槛扫描 M1–M5（命中即 D）
> Step 2 八维评分（对照 references/01-rubric.md，逐项给证据级）
> Step 3 定级（总分 + 底线规则）
> Step 4 出报告（references/03-report-template.md）

### 5.2 命令行评分

```bash
python3 scripts/score.py \
  --scores '{"R1":14,"R2":13,"R3":15,"R4":8,"R5":9,"R6":13,"R7":7,"R8":6}' \
  --scenario default \
  --gates '{"M1":false,"M2":false,"M3":false,"M4":false,"M5":false}'
# 输出：总分 85/100 → S 级 + 底线规则逐项检查
```

`--json` 输出供 CI 门禁集成；退出码 0 正常 / 2 输入错误。

### 5.3 一个完整的评审长什么样

见 `SKILL.md` §使用示例——爬虫 Agent 命中 M1（硬编码 key）判 D，同时给出 4 步修复路径（解锁门槛→补 eval→加预算）。

## 六、设计决策 FAQ

**Q1 为什么不评文档质量？触发词、description 不好也会翻车啊。**
翻车的方式不同：文档差导致"该触发时不触发"（可用性损失），运行时工程差导致"上线后出事"（生产事故）。前者有 10+ 个竞品在管，后者没人管。本技能填的是后者的空位——请把两者配合使用。

**Q2 静态评审不测真实表现，靠谱吗？**
静态评审回答"工程纪律是否就位"，动态评测回答"实际表现好不好"——是两个层次。纪律没就位时不值得跑动态测试（必然埋雷）；纪律就位后动态测试才有意义。两者是"体检"与"体测"的关系。

**Q3 评分会不会很主观？**
双轨评分制 + 证据等级把主观性压到最低：得分 = 检查项达成度基线 − 命中锚，每维记录三行可复核（达成 n/N｜命中锚｜得分），C 级证据由脚本强制 clamp 至 60%。跨 harness 实测曾以同一 rubric 复现出 80 vs 85 的接近结论（差异来源：R2 锚更正 + R3 口径）——分歧可落到具体检查项与适用性判断上核对。

**Q4 为什么 R3（评估闭环）是敏感维度？**
回测中 R3 是最大区分维度（强样本 15、中样本 11、平台 Agent 8）。原因是：评估体系是"其他所有维度的验证器"——没有它，R1-R8 的任何改进都无法确认没改坏。所以它进底线规则。

**Q5 平台型 Agent/Skill 会被低估吗？**
会，结构性低估——它们的 Harness 能力由宿主平台承担。评分细则已补充"平台托管声明按 B 级证据计"，但报告必须注明"平台分未计入"。评审平台技能时请把平台能力纳入人工判断。

## 七、安全与可靠性说明（沙箱与免疫备份核查结论）

**沙箱安全**：
- 本技能**不执行被审对象的任何代码**——纯静态只读评审，天然无执行风险，无需沙箱；
- `scripts/score.py` 经审计：仅 import `argparse/json/sys`，无网络、无文件写入（只写 stdout），退出码干净（0/2）——可直接接入 CI 无隔离执行；
- 未来若扩展"自动扫描被审目录凭据"（M1 半自动化），将坚持只读扫描、永不执行被审脚本的原则。

**免疫备份（三层）**：
1. **版本免疫**：迭代前目录快照（回滚用）——本包非 git 仓，目录快照是唯一回滚路径；
2. **评分免疫**：`evals/benchmark.json` 基准回归——14 用例（5 参照基准 + 3 门槛否决 + 1 M5 门槛样例 + 5 防御回归），规则库被改坏时基准测试立即报警（实测 14/14 PASS，入口 `scripts/run_benchmark.py`）；
3. **发布快照**：发布前用发布流水线的打包脚本打归档 zip（对外分发物）。

回归资产其余两项：探针 **29/29**（入口 `evals/test_v0_1_1_probes.py`）、校准复算 5 样本（入口 `scripts/recompute_calibration.py`）。

**评审过程的可逆性**：本技能全程只读，不在被审对象目录写入任何文件；报告输出到用户指定位置。

## 八、局限性（诚实清单）

- 静态评审不能发现"逻辑正确但运行时崩"的问题（需动态评测补位）；
- 评分含评审者判断成分，重要对象建议双评取中；
- 多 Agent 安全的独有威胁（共谋、责任分散）尚未纳入门槛（拟编为 M6；M5 已占用为"待审内容武器化"）；
- C 级 60% 上限规则尚未在真实付费评审中验证。

### 8.1 校准依据的可得性（可复核什么 / 只能采信什么）

**可自行复核**（随包发布）：
- rubric 全部细则（`references/01-rubric.md`）——8 维检查项与典型证据口径；
- benchmark / 探针 / 复算脚本（`evals/benchmark.json`、`evals/test_v0_1_1_probes.py`、`scripts/run_benchmark.py`、`scripts/recompute_calibration.py`）；
- 样本逐维得分与命中锚（`references/04-calibration.md`、`evals/calibration_cases.json`）。

**只能采信**（不随包发布）：
- 维护者内部评审记录与样本身份档案；
- 跨 harness 主张未在异种 harness 实跑，属同构推理而非实测结论。
